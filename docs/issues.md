## I-05 `post_storage` 失败不回滚，且错误响应不带 `uuid`

**严重程度**：中 ｜ **状态**：部分修复 ｜ **位置**：`src/ffi/storage.rs::fail`

**说明**：已修复：失败路径统一删除本次创建的目录。待讨论：错误响应是否回传 `uuid`。

### 现象

创建目录之后的任一失败（拷贝、压缩、校验、写 `info.json`）都直接 `return write_error(...)`，不清理已创建的 `storage/<uuid>/`。错误信封固定为 `{code, data:{}, msg}`，不携带 `uuid`。

### 影响

- 留下没有 `info.json` 的孤儿目录，`post_get_fil` 对它会返回 `500200`；
- 调用方拿不到 `uuid`，无法主动清理；
- 反复失败会持续累积垃圾目录。

### 修复方向

失败路径统一走清理（删除本次创建的目录）；把 `uuid` 放进错误响应 `data`，或在错误 `msg` 中附带。

## I-06 返回值只表示缓冲区写入状态，业务失败也返回 `0`

**严重程度**：中 ｜ **状态**：待讨论 ｜ **位置**：`src/utils/cjson.rs::write_json_out`、`src/ffi/{storage,info,delete}.rs`

**说明**：三个导出函数只有一套 `int` 返回值，它描述的是「JSON 是否成功写入 `json_out`」，业务结果放在 JSON 的 `code` 里。这是两套编码，调用方容易混淆。

### 现状

`write_success` / `write_error` 都只是拼好 JSON 后调用 `write_json_out`，并把后者的返回值原样返回：

```rust
pub fn write_error(json_out: *mut c_char, code: i32, msg: &str) -> c_int {
    write_json_out(json_out, json!({ "code": code, "data": {}, "msg": msg }))
}

pub fn write_json_out(json_out: *mut c_char, value: Value) -> c_int {
    // 0 = 已写入；-1 = json_out 为空；-2 = 序列化结果 >= 65536 字节
}
```

因此返回码与业务 `code` 的对应关系是：

| 场景 | 函数返回值 | `json_out` 内容 |
| --- | --- | --- |
| 成功 | `0` | `{"code":200,...}` |
| 业务失败（文件不存在、uuid 非法等） | **`0`** | `{"code":400103,...}` |
| `json_out` 为空指针 | `-1` | 未写入 |
| 输出 ≥ 65536 字节 | `-2` | **未写入**，缓冲区内容不确定 |

### 现象

同一个 `0` 既可能是成功，也可能是「文件不存在」。按 C 惯例写出的判断会把错误当成功：

```c
char out[65536];
int rc = post_storage("{\"file_path\":\"missing.txt\"}", out);
if (rc == 0) {
    printf("storage 成功\n");   // 实际 out 是 {"code":400103,"msg":"file does not exist",...}
}
```

正确写法必须先判返回码、再解析 `code`：

```c
int rc = post_storage(req, out);
if (rc != 0) {
    /* 缓冲区问题：-1 空指针，-2 输出过大 */
} else {
    /* 解析 out，再用 json.code 判断业务结果 */
}
```

### 影响

1. **误判成功**：只看 `rc == 0` 会把业务错误当成功，尤其是「文件不存在」「uuid 非法」这类常见错误。
2. **`-2` 时可能读到脏数据**：超长输出时 `write_json_out` 直接返回，`json_out` 未写入，缓冲区里可能是未初始化内容或上一次调用的残留；忽略返回值直接解析会得到错误数据甚至越界读取。
3. **`-1` 与业务错误无法区分**：空指针时连错误 JSON 都写不进去，调用方拿不到任何诊断信息。
4. **两套编码**：返回码 `0/-1/-2` 与业务码 `200/4001xx/5001xx` 语义重叠却不同层级，文档和宿主都容易写错。

### 可选方案

| 方案 | 做法 | 兼容性 |
| --- | --- | --- |
| A. 只强化契约 | 返回值仍只表示缓冲区状态；文档与示例明确「先判返回值，再判 `code`」 | 无破坏，纯文档 |
| B. 业务结果进返回值 | 成功返回 `0`，业务失败返回非 0（如 `1`），缓冲区问题用负数 | 破坏现有宿主：它们可能 `rc == 0` 后不再检查 `code` |
| C. 新增查询接口 | 返回值不变，增加 `ostfil_last_code()` 之类函数 | 不破坏，但多一次调用 |
| D. 新增 `*_v2` | 新函数直接返回业务 `code`，旧函数保留 | 不破坏，接口膨胀 |

### 建议

优先 A（成本最低、无兼容风险）；若希望 C 调用方用单个返回值就能判断，选 C 或 D；B 需要所有宿主同步改造，不建议在 1.x 直接做。

无论选哪个方案，`-2` 分支都应先把 `json_out` 的首字节写 `\0`，避免调用方读到残留数据。
